# Code Style: Afrivate Backend

Last updated: 26 November 2026

These rules describe how the code is written today. Follow them for new code. Do not rewrite working code just to match them.

## Language and framework

- Python 3.11 or newer.
- Django 5.2 with Django REST Framework.
- Settings are in `app/Afrivate/settings.py`.

## Project layout

Each app folder follows the same shape:

```
<app>/
├── models.py          database models
├── serializers.py     input validation and output shape
├── views.py           API endpoints
├── urls.py            routes
├── permissions.py     who may call what (if the app needs custom rules)
├── utils.py           shared helpers (emails, file checks)
├── migrations/        generated by makemigrations, never edited by hand
└── tests.py or tests/ automated tests
```

## Views and permissions

- Use DRF views and set `permission_classes` on every view. Do not rely on defaults alone.
- Filter querysets by the logged-in user, so users only see their own records.
- Return 403 when a user is logged in but not allowed to act on a record. Return 401 when they are not logged in.

## Serializers

- All input validation lives in serializers. Views should not re-check the same rules by hand.
- Use field-level validators (`validate_<field>`) for single fields and `validate()` for rules across fields.

## Errors

- Errors use the shape set by `profiles/utils.py` (`custom_exception_handler`):
  - field errors as `{"field_name": ["message"]}`
  - form-wide errors under `non_field_errors`

## Naming

- Python: `snake_case` for functions and variables, `CamelCase` for classes.
- Models: singular names (`Opportunity`, `Application`).
- URLs: lowercase with hyphens (`/api/auth/verify-otp/`).
- JSON fields: `snake_case` (`opportunity_type`, `is_open`).

## Settings and config

- Read every secret or host value from the environment with `os.environ.get` or `os.getenv`.
- No hard-coded keys, hosts or passwords in code.
- Safe defaults: `DEBUG` defaults to `0`.

## Database changes

- Change models, then run `python manage.py makemigrations`.
- Commit the migration files with the model change.
- Never change the production database by hand.

## Logging

- Use `logging.getLogger(__name__)`. Do not use `print()` in app code.
- Do not log secrets or personal data (see `SECURITY.md`).

## Tests

- Run `python manage.py test` before opening a pull request.
- Every new endpoint needs tests for:
  - success
  - not logged in (401)
  - logged in as another user (403)
  - invalid input (400)

## Comments and docstrings

- Explain why, not what. Keep comments short.
- Public endpoints should have a short docstring. Swagger uses it.

## Commits and pull requests

- Commit messages: short, present tense, describe the change (`Add ownership check to applicant list`).
- One topic per pull request.
